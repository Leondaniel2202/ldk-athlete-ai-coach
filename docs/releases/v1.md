# V1 Release Summary

This document defines what "finished v1" means for the current repository.

## V1 Positioning

V1 is a backend-first foundation that runs alongside a real Notion-based training
workflow.

It is not the final product. It is the point where the backend becomes a serious system
with:

- a relational training model
- a working sync from Notion into PostgreSQL
- read-oriented FastAPI routes
- context-building application services
- backend-owned status and metrics logic
- initial AI analysis on structured context

## Included In V1

- SQLAlchemy models for plans, phases, workouts, sessions, feedback, events, and
  nutrition guidelines
- PostgreSQL and Alembic setup
- one-way Notion sync into the backend
- resource endpoints for plans, phases, workouts, and sessions
- context endpoints for workout, phase week, and full phase snapshots
- AI analysis endpoints for workout and phase context
- unit, integration, and API tests
- developer tooling through `uv`, `Makefile`, ruff, mypy, and pytest
- practical documentation for setup, architecture, domain, operations, and testing

## Explicitly Not In V1

- custom frontend
- write-capable product APIs for planning workflows
- full backend ownership of all business logic
- direct ingestion from Apple Health or other external systems into the backend
- RAG
- AI-generated workouts, phases, or plans
- agentic AI workflows
- multi-user or productized deployment concerns

## Version Naming Clarification

There are three different version labels in the repo and they should not be conflated:

- product/repository `V1`: this release document and the current milestone scope
- API `/api/v1`: the HTTP API version
- living architecture docs: `docs/architecture/current-architecture.md` and
  `docs/architecture/system-map.md`

The architecture docs should normally be updated in place as the current system changes.
If the architecture changes so much that a historical snapshot matters, that snapshot
should be captured explicitly with a dated or milestone-specific file instead of
overloading the API version label.

## V1 Success Criteria

V1 should be considered complete when:

- a developer can set up the project locally from the repo
- the backend can migrate a local database and run cleanly
- Notion sync can populate the local database
- resource and context endpoints can be exercised from synced data
- AI analysis can run when OpenAI credentials are configured
- the test suite, linting, formatting checks, and type checking are part of the normal
  engineering workflow
- the practical documentation is sufficient for a new engineer to understand and operate
  the system

## Known V1 Limitations

- Notion remains the write authority and operational UI
- some business logic still lives outside the backend
- sync is blocking and one-way
- AI is analysis-only
- the product is still optimized for single-user personal use

These are acceptable for v1 because the goal is to establish a clean backend foundation,
not to ship the full independent platform yet.

## Release Checklist

Before tagging or treating the current backend as final v1:

- migrations are current
- `.env.example` matches `Settings`
- `README.md` reflects the actual workflow
- the documentation set above is present and current
- main developer commands work:
  - `make install`
  - `make db-up`
  - `make alembic-up`
  - `make test`
  - `make lint`
  - `make format-check`
  - `make type-check`

## Transition To V2

The roadmap for what comes next is already defined in `docs/roadmap/roadmap.md`.

The major shift from v1 to v2 is:

- moving from backend foundation to usable custom application layer
- increasing backend ownership of planning logic
- making AI a stronger product capability
- beginning frontend validation rather than relying entirely on Notion
